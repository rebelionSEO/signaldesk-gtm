# SignalDesk project continuity

Before substantive work in this repository, read:
1. `docs/PROJECT_BRIEF.md` — durable product requirements and rejected approaches.
2. `docs/WORKING_STATE.md` — current implementation, evidence provenance, blockers and next work.
3. `docs/DECISIONS.md` — accepted decisions versus proposals awaiting review.

These are project memory, not a replacement for the user's latest instructions. If they conflict with a newer user request, follow the newer request and update the documents. Verify runtime, Git status and external facts when needed; memory is not proof that a service is running or a feature works.

## Maintaining continuity
- After meaningful work or user corrections, update working state and relevant decisions before reporting completion. Record what changed, what was actually tested, what remains blocked and the next concrete step.
- Keep the brief stable and concise. Replace stale working state instead of endlessly appending transcripts.
- Mark ideas as proposed, rejected, implemented or verified. Never turn an assistant suggestion into user approval.
- Distinguish product-wide requirements from case-specific presentation. PostHog's voice is not SignalDesk's universal voice.
- Distinguish saved examples, assistant synthesis, API-reviewed research and completed autonomous runs. Never present one as another.
- Before presenting experiments, apply the creative rejection tests in the project brief. A renamed routine task is not a creative idea.
- Reuse saved research. Do not make paid API calls just to reconstruct context. Check explicit spending authorization and remaining test budget before further paid work.
- Do not save credentials, tokens, private client data or raw secret-bearing conversation excerpts in project memory or Git.

Do not change product behavior merely to make memory documents appear true. Record limitations honestly.
